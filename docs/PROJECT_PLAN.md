## 1. 背景与硬约束

### 1.1 起源

项目写于约 2026 年 2 月（历史任务记录集中在 2/23–2/24），未留项目文档、无 git 仓库。当时的硬件局限是：

- **只有一张 16G AMD 显卡**，通过 Ollama 部署本地模型；
- 单卡显存不足以同时常驻多个大尺寸模型，因此整个架构围绕「显存配额」设计；
- 驱动/运行时绑定 AMD ROCm（`rocm-smi`），未做 NVIDIA CUDA 适配。

> 原代码目录名 `main_session`（全局主会话）+ `task_queue`（后台任务队列）与「前台交互 + 后台干活」结构正好对应，说明这是项目一开始就有的意图，只是实现上把两者混在了同一条链路里。原代码里的「查询后台任务数量」内置特例，也正是 v5「顺手看进度」的雏形。

### 1.2 项目定位与最终需求（v5）

> **这是一个「智能本地路由」（Local Intelligent Router），且是「前台 / 后台」双层结构。**

**核心澄清**：

- **4B 是对话前台，始终在线**：用户不管说什么，4B 始终在交互、始终在回复（**句句有着落**）。它负责理解、即时回应、维持对话；**简单任务 4B 自己立刻完成并回复**。
- **真正干活的是后台模型**：复杂任务由中档（8B/9B）或重档（30B/35B MoE）执行；**同一时刻最多一个后台模型驻留**，需要另一档时才把它换掉。
- **等待期间 4B 顺手帮用户看进度**：用户问进度，4B 查后台任务状态并回复。
- **结果直接递回**：后台模型干完后，结果**原样递回给用户，4B 不改写、不整理、不做风格整合**。
- **优先级**：保证功能可用、链路通畅即可，不做过度设计。

**模型池与驻留规则（v5）**

| 层 | 模型 | 角色 | 驻留规则 |
|---|---|---|---|
| 嵌入层 | embedding 模型 | 语义拆解，辅助理解 | **永久常驻** |
| **前台 / 主会话** | **4B**（Q11 已收敛） | **始终交互、即时回复、简单任务直接完成、任务分发决策、进度应答、结果递回**；持有主会话上下文 | **永久常驻，永不换出** |
| 后台 / 中档 | **8B 或 9B**（二选一，Q2） | 复杂任务执行 | **可一直常驻**，需要重档时被换掉 |
| 后台 / 重档 | **30B 或 35B MoE**（Q8） | 高复杂度任务执行 | **可一直常驻**，需要中档时被换掉 |

> **槽位规则（Q16 已关闭）**：后台槽位**允许有一个模型一直常驻**，不必用完立即卸载、不必限时换出；**只有当来了需要另一档模型的任务时才切换**。硬约束只剩两条：① 任何时刻最多 1 个后台模型；② 常驻的那个**必须能被换掉**（不能被锁死，否则另一档任务永远拿不到资源）。
>
> 这比 v4 的「有限驻留窗口 + 加权公平轮换」简单得多，且**切换频率天然最低**——不做无谓换出，正好满足「尽可能不频繁 prefill」。

链路：用户输入 → embedding 语义拆解 → **4B 主会话即时回应** → 简单任务直接答完；复杂任务由 4B 派发到后台槽位异步执行，用户等待期间 4B 应答进度 → **后台结果原样递回**。驱动层同时支持 ROCm 与 CUDA，继续以 Ollama 为推理入口。

**上下文约束（v4 确定）**

- **100K 只是举例，不是写死上限**：窗口长度按**设备实际能力**自适应确定，记为 **N**，无预设天花板；
- N 在一次部署/一次运行时**确定后即固定**，所有模型统一，**运行期不随模型切换变动**、不回落 Ollama 默认值；
- 用户**接受切换后重新 prefill**，目标为「尽可能不频繁 + 可观测」。

> **原设计缺陷（用户已确认）**：**1.5B 生成式模型做「5 行模板拆分」**是设计问题，明确废弃，由 embedding 语义拆解替代；相关代码与三个未使用的专用拆分模板一并清理。

### 1.4 物理约束与显存预算（估算，须实测校准）

| 角色 | 模型 | 权重显存估算 | 含 KV/上下文的预留 | 16G 卡可行性 |
|---|---|---|---|---|
| 嵌入层 | embedding | 0.3–1 GB | ~1 GB | 常驻 |
| 前台 | 4B | 2.5–3.5 GB | 取决于 N | 常驻 |
| 后台中档 | 8B / 9B | 5–6.5 GB | 取决于 N | 槽位常驻，与常驻组合合计约 11–13 GB，勉强可行 |
| 后台重档 | 30B / 35B MoE | **18–22 GB** | 取决于 N | **16G 卡无法全量载入**，见 1.5 |

> **v5 注意**：因为允许一个后台模型常驻，显存是「常驻组合 + 一个后台模型」的**稳态占用**，不是瞬态峰值——预算按稳态算，反而更容易预测。但 **KV(N) 可能比权重更紧**，全部数值须 P0 实测后重写。

### 1.5 MoE 专项分析（沿用）

选 30B/35B MoE 的道理：「35B」是**总参数量**，推理只激活少数专家（如 A3B 类约 3B 激活），算力需求接近小模型。但**全部权重仍需可寻址**——Q4 权重约 18–22 GB（估算），16G 显存放不下，Ollama 不会因稀疏激活就只加载被激活的专家。

| 路径 | 做法 | 代价 | 待验证 |
|---|---|---|---|
| A（首选） | **测试机换更大显存卡**（≥24G，最好 32G+） | 依赖用户指配；若成立，1.4 预算表重写 | Q9 |
| B | **CPU offload**：`num_gpu` 只放部分层 | 首 token 延迟/吞吐大幅下降，依赖系统内存 | Q10 + P0 实测 |
| C | 更低比特量化（Q3/Q2/IQ 系列） | 质量下降，未必压得进 16G | P0 实测 |
| D | 专家级懒加载 / 流式换入 | 工程量大，一期不做 | 仅记录 |

**P0 第一号 go/no-go**：确认测试机显存与系统内存、MoE 型号/量化/激活参数，实测「能否加载、以什么方式、首 token 延迟多少」。

### 1.6 上下文自适应、前台/后台分离与切换成本

#### 1.6.1 N 怎么定：设备自适应，而非硬编码

```
N = min(
      设备可容纳的上下文长度（由显存/内存预算反推 KV cache 容量）,
      所有候选模型支持的最大上下文窗口 (取最小者),
      Ollama 该版本/该模型允许的有效 num_ctx
    )
```

- 启动时（P0 部署阶段）**探测一次并确定 N**，写入运行配置；不同设备可以有不同的 N；
- **同一次运行内 N 是常量**，下发给所有模型，运行时禁止改动（Ollama 改 `num_ctx` 会触发重载、窗口漂移）；
- 取「所有候选模型支持窗口的最小值」保证切换时不会出现某模型截断或报错；
- 不预设 100K，也不预设天花板，具体数值以 P0 实测为准。

#### 1.6.2 一个绕不开的架构事实（用户已接受）

**KV cache 与模型权重绑定**：层数、注意力头结构（GQA/MQA）、`head_dim`、量化决定每层 K/V 形状。换模型 = 换权重 = 旧 KV cache 全部失效。

| 目标 | 结论 |
|---|---|
| 窗口长度 N 恒定、不随切换变动、不回落默认值 | ✅ 可严格保证 |
| 会话上下文连续、不丢历史 | ✅ 可保证（且因 4B 常驻而天然成立） |
| 切换模型后完全不重新 prefill | ❌ 做不到，KV cache 不可跨模型复用 |
| **尽可能不频繁 + 可观测** | ✅ **用户已接受此目标** |

> **v5 简化了达成路径**：允许一个后台模型一直常驻 → 只有「需要另一档」才切换 → 切换次数自然最少，无需额外的驻留窗口/轮换机制。

#### 1.6.3 前台/后台上下文分离（核心设计）

| | 主会话上下文（前台） | 后台任务上下文 |
|---|---|---|
| 持有者 | **4B 主会话 + `ContextStore`（按 `session_id`）** | 槽位模型（一次性） |
| 内容 | 完整多轮对话历史、语气、偏好 | 4B 打包的**短任务包**：任务描述 + 必要片段 + 约束 + 输出要求 |
| 是否随切换变动 | **不变**：4B 永不换出，上下文天然连续 | 每次切换重建，但长度短、可控 |
| 切换代价 | 无 | 一次短 prefill（用户已接受） |

- 4B 始终在交互，主会话上下文从不需要在模型间搬运；
- 复杂任务不是「把整段会话丢给后台模型」，而是由 4B 提炼成短任务包再派发，后台模型是**无状态执行器**；
- 结果**原样递回**，4B 不做整合改写（v5 简化）；
- 「反复预装填」即便发生，装的也是短任务包而非 N 长度会话——架构自带，不需要额外的摘要压缩机制。

#### 1.6.4 切换策略（v5 简化）

- **默认不切**：当前驻留的后台模型一直常驻，同档任务直接复用（零切换、可复用前缀缓存）；
- **按需切换**：只有当任务需要另一档模型、且当前档队列排空（或等待超上限）时，才卸载当前、换入目标；
- **可达性保障**：为避免某个常驻模型把另一档任务无限饿死，保留一条简单规则——**另一档任务等待超过阈值即强制切换**（不是加权公平轮换，不做计时窗口）；
- **可观测**：每次切换记录 `prefill_tokens`、prefill 耗时、换入耗时、N 快照、切换原因；日志按 `session_id` + `task_id` 串联；
- **不做**：有限驻留窗口计时、连续驻留上限、轮换计数、预热/独占时段开关、批量合并优化（见 2.5）；
- 运行期常驻 ≠ 开机自启，与用户「禁止后台自启」偏好不冲突；**禁止**清模型缓存（`restart_ollama.sh:21-22`，P2-11）。

### 2.3 歧义与收敛状态

- **embedding 拆解形态**（Q1）：解读 A = 向量 + 相似度粗分类、检索样本辅助 4B 理解（倾向采用）；解读 B = 仍输出结构化文本。`EmbeddingProvider` 抽象兼容两种。
- **前台模型选型（Q11，已收敛）**：用户明确主张 **4B 常驻**（需要始终在线的快速回复）。型号仍可配置。

### 2.4 明确不做（本轮）

- 不在当前 Windows 机上运行项目；不擅自连接远程设备、装驱动、改系统配置；
- 不预设具体模型品牌/量化/驱动版本；不预设固定的 100K 上下文；不实现知识库问答产品化；不实现专家级懒加载；
- **不实现「跨模型 KV cache 复用」**（架构不可行，用户已接受重新 prefill）；
- 不把完整会话历史灌给后台模型（改发短任务包）。

### 2.5 复杂度收敛清单（v5 新增，用户明确要求「不需要太麻烦」）

> 优先级：**保证功能可用、链路通畅 > 一切优化**。以下项目从 v1–v4 方案中**移除或后置**，不进入一期范围：

| 移除/后置项 | 原方案 | v5 处理 | 理由 |

## 5. 目标架构设计

### 5.1 分层（v5 简化）

```
客户端（请求带 session_id）
  │  /chat  /task_result  /health  /models  /gpu  /tasks
  ▼
API 层            FastAPI（鉴权、限流、输入校验、链路 ID）
  ▼
上下文层          ContextStore（Redis，按 session_id 持有主会话历史）
                  全局 N = 设备自适应确定，运行期恒定
  ▼
【前台·永久常驻】  embedding 语义拆解（替代 1.5B）
                  4B 主会话：句句有着落 · 即时回复
                     ├─ 简单任务 → 自己直接答完（零切换）
                     ├─ 复杂任务 → 打包短任务包派发后台
                     ├─ 等待期间 → 查 task_status，应答进度（F12）
                     └─ 后台结果 → 原样递回，不改写
  ▼                        │ 派发                    ▲ 结果递回
编排层            Router（复杂度 × 实时显存 × 是否需要换档）
  ▼
【后台·槽位】      【最多 1 个】默认一直常驻
                  需要另一档时才切换：8B/9B ⇄ 30B/35B MoE
                  无状态执行器，只接收一次性短任务包
  ▼
资源层            GPUBackend（ROCm | CUDA | Ollama ps | CPU）
                  VRAMBudget（权重 + KV(N)）+ VRAMLease
  ▼
执行层            Celery 队列 + Worker（后台任务）
```

### 5.2 GPU 驱动抽象（沿用）

`GPUBackend` 接口 `detect/total_mb/used_mb/free_mb/describe`；`RocmBackend`（`rocm-smi --showmeminfo vram`）、`CudaBackend`（`nvidia-smi --query-gpu=...` 或 NVML）、`OllamaPsBackend`（`/api/ps` 对账兜底）、`CpuBackend`（无 GPU 明确报错）。探测顺序：环境变量 `GPU_BACKEND` → CUDA/ROCm → Ollama ps → 失败即启动失败并给诊断信息。`/health`、`/gpu` 暴露后端与显存。驱动补齐清单按目标机型号与 Ollama 官方文档确认。

### 5.3 嵌入层（纠正 1.5B）

`EmbeddingProvider`：`embed(text) -> vector`、`split(text) -> SemanticSplit`；默认走 Ollama embeddings API，候选待目标机模型清单确认；永久常驻。删除 `MODEL_SPLIT`（1.5B）、`first_split_template` 调用链、三个废弃模板。chroma few-shot 后置（2.5）。

### 5.4 前台主会话层（v5 简化，核心）

**4B 永久常驻，是用户始终在对话的对象。**职责：

1. **句句有着落**：每条用户输入都先由 4B 产生回应，不等后台模型；
2. **简单任务直接完成**：日常闲聊、简单问答、轻量文本由 4B 立刻回复，**不触发槽位切换、零换入成本**；
3. **任务分发决策**：结合 embedding 拆解与会话上下文，判断是否需要后台执行、期望档位；输出结构化 JSON 便于校验兜底；
4. **任务包打包**：复杂任务提炼为自包含短任务包（任务描述 + 必要片段 + 约束 + 输出要求 + `session_id`/`task_id`），不灌整段会话；
5. **进度应答（F12）**：等待期间用户发消息或问进度，4B 查 `task_status` 后回复当前状态/进度/当前档位/预估等待；**改造原关键词短路特例**（P2-6），不再硬编码文案、不误伤正常提问；
6. **结果原样递回**：后台模型干完后，`final_reply` 直接是该模型输出，**4B 不改写、不整理、不做风格整合**（用户明确要求）；
7. **持有主会话上下文**：4B 永不换出，主会话上下文天然连续，N 恒定。

> 4B 常驻的价值不只是省一次加载，而是让「始终交互」和「上下文连续」同时成立；而结果透传让链路最短、最不容易出错。

`Router.select(intent, complexity, gpu_snapshot, slot_state, queue_state)`：

1. 4B 判定「简单任务」→ **直接回复，结束**（最常见路径，零切换）；
2. 复杂任务 → 期望档位；重档需过复杂度门槛；
3. 资源层：`usable = min(真实空闲显存, 逻辑预算剩余) - reserve - headroom`，校验「权重 + KV(N)」放得进；
4. **期望档位 == 当前常驻档位 → 直接复用，零切换**（最常见后台路径）；
5. 期望另一档 → 等当前档队列排空（或另一档等待超 `starvation_timeout_s`）→ 卸载当前、换入目标；超时沿 `MoE → 中档 → 4B` 降级；
6. 返回 `SelectionResult(tier, model, slot_action, wait_estimate_s, reason)` 写入响应与日志。

### 5.6 槽位切换与可观测（v5 简化）

- `SlotManager` 用 Redis 分布式锁保证最多 1 个后台模型；前台不占槽位。
- **默认不切**：当前档一直常驻，同档任务直接复用（可复用前缀缓存，按 Ollama 版本核实）。
- **按需切换**：仅当需要另一档任务、且队列排空或等待超阈值时才换出；不做计时窗口、不做轮换计数、不做加权公平调度。
- **可达性**：`starvation_timeout_s` 保证常驻模型能被换掉，另一档不会无限等待。
- **可观测**：每次切换记录 `prefill_tokens`、prefill 耗时、换入耗时、N 快照、切换原因；日志按 `session_id` + `task_id` 串联。
- **禁止**清模型缓存（P2-11）；不做预热/独占时段（2.5）。

### 5.7 配额、状态与响应语义（修 P0-1/P0-2/P2-12）

- `VRAMLease`：`with lease(model) as l:` + `try/finally` 归还；Redis Lua 原子；TTL 租约防崩溃泄漏。
- **预算 = 权重显存 + KV(N) + 预留**，按稳态（常驻组合 + 1 个后台模型）计算；真实显存与逻辑预算取小，定期与 `/api/ps` 对账。
- 状态机：`pending → processing → completed | failed | retrying | cancelled`，同步/异步共用 `finalize_task()`。
- **`/chat` 响应语义（Q17 已关闭）**：
  - **始终立即返回**，含 `instant_reply`（4B 的即时回应，保证「句句有着落」）；
  - 简单任务：`process_mode: "direct"`，`instant_reply` 即最终答案，无 `task_id`；
  - 复杂任务：`process_mode: "async"` + `task_id` + `instant_reply`（4B 的一句即时回应，让用户先等着）；后台完成后 `final_reply` = **后台模型原始输出**，通过 `/task_result` 获取，**不做任何改写**；
  - 等待期间用户发消息：4B 应答进度（F12），仍是 `instant_reply`；
  - **兼容性**：保留旧字段（`最终回复` 等），新增字段只追加；统一 200，避免旧客户端把 202 当异常。

### 5.8 队列与调度治理

- 阈值统一为「空闲显存 MB」，删除百分比双语义（P1-1/P1-2）；明确 worker 池类型，并发与 `usable` 联动（P1-4）。
- `add_consumer`/`cancel_consumer` 前校验节点名（P2-5）；`re` 移到模块顶部（P2-4）。
- **简单任务根本不进队列**（4B 直接处理），队列压力小；重档任务可给单独队列或优先级标签，避免被中档任务堵住。

### 5.9 工程化与兼容性

- 配置外置 + 环境变量覆盖，删除 `/home/liuda/...` 硬编码（P1-6）。
- API 向后兼容：旧字段保留，新增 `session_id`、`instant_reply`、`process_mode`、`chosen_model`、`tier`、`resolved_num_ctx`、`gpu_snapshot`、`selection_reason`、`prefill_tokens`。
- 结构化日志 + 链路 ID；记录换入换出、prefill 长度与耗时、KV 峰值、N 快照、进度查询。
- 安全：绑定地址与 token 可配、输入长度限制、prompt 中用户输入做明确分隔。
- 启停脚本：幂等、PID 文件、健康检查、优雅停止、**不含任何 enable/自启逻辑**。
- 依赖瘦身，补 `requests`/httpx 与 pytest；区分 runtime / dev。

### P3 前台主会话层与上下文状态层

- **任务**：`EmbeddingProvider` 替代 1.5B；**4B 主会话常驻化**（`keep_alive` 永不过期、句句有着落）；删除 1.5B 配置与废弃模板；新增 `ContextStore` + `session_id` + `messages` 多轮调用；**实现「简单任务 4B 直接回复」与 `/chat` 即时响应语义**（P2-12）；4B 输出结构化分发决策；**把 P2-6 的关键词短路改造为进度应答 F12**。
- **验收**：
  1. **每条用户输入都在短时间内收到 4B 的即时回复**，不等后台模型；
  2. 简单任务由 4B 直接完成，**不触发槽位加载**；
  3. 等待期间问进度，4B 能返回该任务的状态/进度/当前档位，且不会误伤正常提问；
  4. 同一 session 连续多轮历史不丢、`num_ctx` 恒定为 N；embedding 与 4B 多次请求后仍驻留；
  5. 固定样例集上分发决策（简单/中/重）符合预期。
- **回滚**：`feature_flags.use_embedding_split=false` 临时切回旧链路；`feature_flags.frontend_instant_reply=false` 临时回退到「等生成完再返回」。

### P4 后台槽位与结果递回（v5 简化）

- **任务**：`config/models.yaml` 前台 + 槽位 + N/KV 预算；`Router` 决策与降级链；**任务包打包/解析**；`SlotManager`（互斥锁 + 默认常驻 + 按需切换 + 等待超时强制切换）；`OllamaModelManager`（load/unload/offload/keep_alive）；**后台结果原样写回 `final_reply` 并递回**；prefill/切换指标可观测。
- **验收（以链路通畅为准）**：
  1. 复杂任务：4B 即时回应 → 后台执行 → 结果原样递回，全链路按 `session_id`/`task_id` 可追踪，**4B 不改写结果**；
  2. 槽位内**任何时刻只有 1 个后台模型**；**默认常驻不做无谓换出**；来了需要另一档的任务能成功切换，且不会因常驻而无限等待；
  3. 多次 A→B→A 切换后，`num_ctx` 始终为 N、主会话历史连续；后台只收短任务包，`prefill_tokens` 显著小于 N；
  4. 每次切换的 `prefill_tokens`/耗时有日志可查；
  5. 权重 + KV(N) 不超稳态预算、无 OOM；重档按 P0 结论运行，不可行时按策略降级/排队并给出明确原因。
- **回滚**：`feature_flags.multi_tier=false` 固定单一中档；重档整体禁用；槽位可退化为「一次只加载一个、用完即卸」。

### P5 稳定性、测试与交付

- **任务**：超时/重试/取消、鉴权与输入约束、结构化日志与指标、pytest 单元+集成、并发压测、README/架构说明/运维手册/回滚脚本、清理 P3 冗余文件。
- **验收**：测试全绿；并发压测下无配额泄漏、无状态悬挂、无窗口漂移；旧 API 字段回归通过；文档可独立完成新机部署。**不做 2.5 列出的后置优化**。

```
P0（等待地址；两个 go/no-go：MoE 可行性 + 确定 N / KV 预算）
 └─ P1 止血（含 num_ctx 统一）─┬─ P2 驱动抽象 ─┬─ P3 前台主会话 + 上下文 + 进度应答 ─ P4 槽位/结果递回 ─ P5 交付
```
